# Git and Commit Workflow

## Branch policy

`main` is the releasable branch and should remain runnable. Focused feature/fix branches are recommended for non-trivial work. Do not force-push `main` and do not rewrite published release tags.

## Commit scope

Use one logical concern per commit. Split unrelated documentation, bug fixes, recipe work, packaging, and cleanup when that separation improves rollback or review.

Preferred prefixes:

- `feat:` new user-visible capability;
- `fix:` defect correction;
- `refactor:` internal restructuring without intentional behavior change;
- `test:` regression/test-only change;
- `docs:` documentation-only change;
- `build:` packaging, CI, install/update/release infrastructure;
- `chore:` narrowly scoped maintenance/housekeeping;
- `release:` version release commit generated by the release script.

Examples:

```text
feat: add multi-intersection coordinate templates
fix: preserve axis bounds in migrated implicit plots
docs: document Plugin distribution contract
build: add GitHub regression workflow
release: v0.9.0
```

## Before committing

1. `git status --short` — confirm no unrelated changes.
2. `git diff` — inspect the actual patch.
3. `./scripts/check.sh` for behavior/runtime changes.
4. `git diff --check` — no whitespace errors.
5. Ensure generated PDFs, caches, `.funfig`, fonts, or non-canonical icon exports are not staged.

Do not use a cleanup commit to hide unrelated modifications. Do not silently discard user-authored files.

## Push policy

Push normal development commits to the intended branch. Releases use `./scripts/release.sh`; do not manually create a competing release tag/version. Tags `vX.Y.Z` are immutable publication references.
